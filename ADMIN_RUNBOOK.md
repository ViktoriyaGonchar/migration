# Runbook для администратора и оператора

Кросс-ссылки: [README.md](README.md) · [TESTING.md](TESTING.md) · [DEPLOY.md](DEPLOY.md)

Документ для **сопровождения**, не для разработки. Команды сервера — по вашему runbook инфраструктуры; CLI: **`mc-cli`**, **`mc-bot`** из [`pyproject.toml`](pyproject.toml).

## Как читать очередь заявок

1. Войти в **SQLAdmin** (`/admin`) под учётной записью администратора.
2. Открыть раздел ручных платёжных заявок (очередь / список заявок — название в меню админки).
3. Обратить внимание на статус (**pending**, одобрено, отклонено и т.д.) и время создания.
4. Если настроен **Phase 9**: сводка по «зависшим» pending и предупреждение по **самой старой** заявке в pending сверх порога **`STALE_PENDING_ALERT_HOURS`** (часы в UTC). Это сигнал «заявка долго без решения», а не автоматический сбой.

**Ожидаемый результат:** видна полная картина по необработанным заявкам.

**Если пусто при ожидаемых заявках:** проверить фильтры в списке; убедиться, что пользователь создал заявку через тот же контур (ручной перевод, не путать со stub).

## Approve и reject — это не grant

- **Одобрить (approve)** или **отклонить (reject)** заявку — это решение по **факту оплаты / заявке** в очереди. Оно **не заменяет** выдачу доступа на сайт.
- **Выдача доступа (grant)** и **новая login-ссылка (reissue)** — **отдельные действия** (страница **Operator** в админке или команды `mc-cli grant-access` / `reissue-link` по внутренней политике).

**Типичная ошибка:** одобрить заявку и ждать, что подписка продлится сама. **Проверка:** после approve выполнить grant/reissue согласно регламенту.

## Страница Operator

- Назначение: выдача или продление доступа (**grant**), перевыпуск ссылки входа (**reissue**) для известного подписчика.
- Перед действием убедитесь в правильном **subscriber_id** (путаница ID — частая причина инцидента).
- После операции проверьте срок подписки или что новая ссылка открывается у пользователя.

Подробные сценарии проверки: [TESTING.md](TESTING.md).

## Stale pending и summary

- **Stale** в контексте админки — заявки, висящие в **pending** дольше порога (по умолчанию в `app/config.py`; переопределение — `.env.full.example`, `STALE_PENDING_ALERT_HOURS`).
- Summary на странице очереди помогает быстро увидеть количество и «возраст» проблемных заявок **в UTC**.

**Если алерт горит постоянно:** либо реально не успеваете обрабатывать очередь, либо порог слишком жёсткий для процесса — согласовать изменение порога с владельцем продукта (не менять код в поле runbook).

## CSV export

- Если в интерфейсе очереди есть выгрузка **CSV**, используйте её для отчётов и сверок.
- Открывайте в редакторе с учётом кодировки (UTF-8).

**Если файл пустой или обрезан:** повторить с меньшим фильтром; при таймауте — обратиться к сопровождению инфраструктуры.

## Уведомление в Telegram не ушло

1. Проверить, что в `.env` задан **`ADMIN_NOTIFY_TELEGRAM_IDS`** (список chat_id через запятую).
2. Админы должны были нажать **/start** у бота (или бот в группе с нужными правами).
3. Посмотреть логи процесса **`mc-bot`**: ошибки httpx, таймауты, ответы internal API.
4. Убедиться, что backend доступен с хоста бота по **`INTERNAL_API_BASE_URL`** и ключ **`INTERNAL_API_KEY`** совпадает.

**Ожидаемый результат после исправления:** новая тестовая заявка снова порождает уведомление.

---

## Ротация internal API key

1. Сгенерировать новый ключ, обновить **`INTERNAL_API_KEY`** в окружении **backend**.
2. **Синхронно** обновить тот же ключ у процесса **`mc-bot`** (и любых других клиентов internal).
3. Перезапустить процессы в любом порядке, но минимизировать окно, когда ключи различаются (кратковременные 401 ожидаемы).
4. Не хранить старый ключ в логах и тикетах.

Подробнее про сеть и секреты: [DEPLOY.md](DEPLOY.md).

## SQLite locked

**Симптомы:** ошибки базы о блокировке, таймауты записи.

**Действия:**

1. Убедиться, что нет второго процесса с другой БД по ошибке (два разных `DATABASE_URL`).
2. Не запускать тяжёлые отчёты на живой файле без read-only копии.
3. Для бэкапа — предпочтительно остановить процессы или использовать механизм онлайн-бэкапа SQLite по политике [DEPLOY.md](DEPLOY.md).
4. Если инцидент повторяется — эскалация на разработку/инфраструктуру (WAL, диск, антивирус на файле БД).

## Backup / restore basics

- **Бэкап:** скопировать файл базы (путь из `DATABASE_URL`) в безопасное место; лучше при остановленных `uvicorn` и `mc-bot` или по согласованной процедуре.
- **Восстановление:** остановить сервисы, заменить файл, поднять, проверить `/health` и выборочно админку. Полный чеклист: [TESTING.md](TESTING.md) (раздел backup на копии).

## Короткий incident checklist

1. **Сайт недоступен** — `/health`, процесс uvicorn, proxy, диск.
2. **Бот молчит** — процесс `mc-bot`, `BOT_TOKEN`, сеть до API.
3. **Заявки не создаются** — бот, internal ключ, логи backend.
4. **Очередь растёт** — загрузка операторов; stale summary; не путать approve с grant.
5. **Пользователь «оплатил, нет доступа»** — статус заявки; выполнен ли grant; срок подписки; новая ссылка `reissue-link`.

## Опасные действия / не делать

- Удалять записи в БД вручную без понимания связей и бэкапа.
- Менять **`TOKEN_PEPPER`** на работающей системе — обнулит действующие login-токены.
- Одобрять заявки без сверки оплаты по регламенту.
- Выдавать grant не тому **subscriber_id**.
- Копировать файл SQLite с работающего сервера «как есть» без процедуры и надеяться на целостность.
- Включать **mock/sandbox** платежи на реальных пользователях без отдельного решения.
- Светить **`INTERNAL_API_KEY`** в тикетах и скриншотах.
